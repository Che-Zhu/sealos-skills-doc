## Source types

| Source | Detection | Required tools |
| --- | --- | --- |
| Official template | Phase 1 exact catalog match (fast path) | None (fast path) |
| Docker Compose | `.sealos/phase-2/docker-compose.yml` (Phase 2 canonical) | kompose |
| Helm | `Chart.yaml` or chart directory | Helm 3+ |
| Kubernetes | Single native manifest file | Python/PyYAML |

On the standard build path, Phase 2 writes `deployment_source` in `deployment-plan.json`. Phase 4 reads that pointer directly — no second scout.

## Source selection priority

Phase 2 picks **one** `deployment_source` after scout:

1. **Helm** — chart root directory
2. **Kubernetes** — single manifest file
3. **Compose** — generate or normalize to `.sealos/phase-2/docker-compose.yml`

When Helm and Kubernetes both exist, Helm wins. When multiple sources of the same kind conflict, resolve the primary topology from README, CI, or docs — do not guess.

One Sealos deploy must cover every relevant component (databases, queues, caches, workers). Phase 4 must not drop dependencies because they are not the main app.

## Conditional source materialization

Git LFS, submodules, and similar mechanisms are installed and fetched only when the repository declares them. See [Phase 0](/en/pipeline/phases/phase-0-preflight).

## Topology preservation

The file (or chart render) at `deployment_source` must include the full runtime topology. Build-only handling is separate from final runtime topology; Phase 3 digests are written back to matching workloads in Phase 4 from `analysis.json` → `build_result`.
