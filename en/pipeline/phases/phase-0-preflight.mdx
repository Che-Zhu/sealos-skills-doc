## Purpose

Phase 0 checks that the environment can run `sealos-deploy`. It resolves the project source, materializes source code, and writes `runtime_profile`, `work_dir`, `repo_name`, and `github_url` to `.sealos/analysis.json`.

Phase 0 does not judge deployability. It does not build images. It does not generate templates. It does not create cloud resources.

## Inputs

| Input | Source |
| --- | --- |
| `SEALAI_DEPLOY_TASK_ID` | Process environment |
| Host environment | OS and package managers |
| Project source | Skill argument: GitHub URL, local path, or `$(pwd)` when omitted |

## Outputs

| Output | Description |
| --- | --- |
| `.sealos/analysis.json` | Contains `runtime_profile`, `work_dir`, `repo_name`, `github_url` |
| Deploy log | Phase boundaries from this phase onward |
| Result | `CONTINUE` or `STOP` |

## Preconditions

None.

## Procedure

### 1. Set `runtime_profile`

| `SEALAI_DEPLOY_TASK_ID` | `runtime_profile` |
| --- | --- |
| Present | `sandbox` |
| Absent | `local` |

### 2. Install required dependencies

A `sealos-deploy` invocation means the user agrees to install dependencies. If a tool is missing, install or upgrade it now. Do not ask per tool. Recheck after install.

**`local` and `sandbox`:**

Git, Git LFS, Node.js 18+, Python 3.8+ and PyYAML, [gitingest](https://pypi.org/project/gitingest/) (`pip install gitingest`), kompose, Helm 3+, kubectl, curl, jq

**`local` only:**

`gh`, Docker CLI, a running Docker daemon, Docker Buildx, [railpack](https://github.com/railwayapp/railpack)

`sandbox` includes railpack. On `local`, install or upgrade railpack and confirm `railpack --help` works.

If Docker is installed but the daemon is not running, start the daemon.

**`local` auth only:**

If `gh` is not logged in or lacks `write:packages`, complete login or authorization. Confirm kubeconfig for the selected workspace.

### 3. Confirm platform context (`local` only)

1. Select the Sealos Cloud region.
2. Complete Sealos login.
3. Select the target workspace.

Update Sealos auth and kubeconfig in the user home directory.

`sandbox` skips this section. Kubernetes permissions, `GITHUB_TOKEN`, S3, and other injected values are checked in later phases when needed.

### 4. Resolve project source

| Source | Action |
| --- | --- |
| GitHub repository URL | Clone to a temporary directory |
| Local project directory | Use the given path |
| No argument | Use `$(pwd)` |

Resolve `repo_name`. If a GitHub remote exists, record `github_url`. Step 6 writes both fields to `analysis.json`.

### 5. Materialize source

Materialize the full workspace for the current commit. Fetch submodules and LFS objects. Recheck after materialization.

For a local directory source, keep existing modifications.

A README command alone must not trigger tool installation.

### 6. Write `analysis.json`

```bash
mkdir -p "{work_dir}/.sealos"
```

Write `.sealos/analysis.json`:

```json
{
  "runtime_profile": "local",
  "work_dir": "/path/to/project",
  "repo_name": "my-app",
  "github_url": "https://github.com/owner/repo"
}
```

| Field | Description |
| --- | --- |
| `runtime_profile` | Same as step 1: `local` or `sandbox` |
| `work_dir` | Absolute path to an analyzable, buildable workspace |
| `repo_name` | Directory name or URL parse result |
| `github_url` | From the argument or `git remote`; `null` for non-GitHub projects |

At the end of Phase 0, the file contains only these fields. Phase 1 writes `official_template`. Phase 2 writes `deployment_plan`. Phase 3 writes `build_result` (only after this phase actually runs).

### 7. Start the deploy log

Create the deploy log. Record Phase 0 boundaries and key decisions. Later phases append to it.

## Stop conditions

| Result | Condition |
| --- | --- |
| **STOP** | `runtime_profile` cannot be determined |
| **STOP** | A required dependency cannot be installed or verified |
| **STOP** | `local`: region, login, or workspace not confirmed |
| **STOP** | Project source cannot be resolved or source materialization fails |
| **STOP** | `analysis.json` cannot be written |
| **CONTINUE** | All checks pass → [mode detection](/en/pipeline/mode-detection) |

## Acceptance

- `runtime_profile` is `local` or `sandbox`
- Required dependencies are installed and available
- `local`: Sealos region, login, and workspace are confirmed
- `.sealos/analysis.json` exists with `runtime_profile`, `work_dir`, `repo_name`
- `work_dir` is complete, analyzable, and buildable

## Schema links
