## Purpose

Phase 3 **executes** build and push: parse `deployment_source` from `deployment-plan.json`, then build and push images for workloads that still lack a reusable digest and need a local build. One service needing build does not discard already verified images for other services.

This phase does not scout the repo, generate Dockerfiles, or modify `deployment_source` (recipe errors return to Phase 2).

Docker, Buildx, Node.js 18+, and `gh` are required only when this phase actually runs.

## Inputs

| Input | Source |
| --- | --- |
| Deployment source | Phase 2 `deployment_plan` → `deployment_source` |
| Build targets | Parsed from deployment source (see table below) |
| Caller | Phase 4 entry branch (when build is required) |
| GitHub auth | Phase 0 (`local`) |

### Parse build targets from `deployment_source`

| Source type | How to parse |
| --- | --- |
| Compose (`.sealos/phase-2/docker-compose.yml`) | Each service with `build:` |
| Helm (chart directory) | After `helm template`, workloads whose images need local build |
| Kubernetes (single yaml) | Containers in the manifest that need local build |

## Outputs

| Output | Path | Description |
| --- | --- | --- |
| Per-service build result | `.sealos/build/{service-key}/build-result.json` | Digest, pull access, push metadata; key aligns with service/workload name in deployment source |

## Procedure

Sealos Deploy must:

- Push newly built images to the current GitHub user's GHCR. The user does not choose the registry.
- Check `gh` login and `write:packages` only when builds are pending.
- Build for `linux/amd64`.
- For each build target, run Buildx with context and Dockerfile paths declared in the deployment source.
- Tag with a unique version identifier per build.
- Read digest from Buildx metadata for the same build.
- Record whether anonymous pull works and whether deploy needs a pull secret.
- Return recipe failures (missing Dockerfile, invalid context, Dockerfile syntax errors) to Phase 2 step 3. Keep auth, network, Docker, and push failures in Phase 3.

Pull failures on Dockerfile bases during build are recipe failures. Push failures to `ghcr.io/{user}/...` are Phase 3 execution failures.

All private or indeterminate GHCR images in one app must share one normalized GHCR namespace. Mixed namespaces stop before cloud resource creation.

Components with upstream images and resolved digests are not rebuilt here. New builds from this flow go to GHCR only.

`build-result.json` passes `push.pull_access` to Phase 4. Only `ghcr_secret_required` or `indeterminate` successful builds attach pull-secret handling in the template.

## Stop conditions

| Result | Condition |
| --- | --- |
| **CONTINUE → Phase 4** | All required builds succeed or no builds were needed |
| **RETURN → Phase 2** | Build recipe failure for a service |
| **STOP** | Phase 3 execution failure after remediation, or namespace conflict |

## Acceptance

- Each built service has `build-result.json` matching schema
- Digests are immutable `repository@sha256:...`
- Upstream image references that were not rebuilt are unchanged
