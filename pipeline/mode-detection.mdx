[Phase 0](/pipeline/phases/phase-0-preflight) 完成后，读取 `.sealos/analysis.json` 中的 `work_dir` 与 `github_url`，判断本次运行是**首次部署**还是对已有应用的**更新**。

## 部署模式识别步骤

Agent 必须按以下顺序执行：

1. **恢复桥接状态**（仅 `analysis.json` 中 `github_url` 非空且 `work_dir` 为本次克隆的临时目录）：从 `~/.sealos/deployments/github.com/<owner>/<repo>/state.json` 恢复到 `work_dir`。
2. **读取部署状态**：读取 `.sealos/state.json`。若存在 `last_deploy`，进入步骤 4。
3. **集群发现**（无 `last_deploy` 时）：用 kubectl 在工作空间查找与项目匹配的旧部署。发现完整且无歧义匹配时，向用户确认并写入 state，再进入步骤 4。用户否认或无匹配 → **DEPLOY 模式**。
4. **验证线上状态**：对每个 `last_deploy.services[]` 工作负载确认容器仍在运行，且镜像 digest 与记录一致。kubectl 不可用时告知用户并进入 **DEPLOY 模式**。状态与集群矛盾时停止并让用户核对，不得静默新建重复部署。
5. **用户选择**：展示应用、工作负载、镜像 digest 与访问 URL。用户选择更新（**UPDATE**）或新建实例（**DEPLOY**）。

仅含已完成一次性 Job、无可更新工作负载时，只提供新建部署选项。

## DEPLOY 模式

首次部署运行 Phase 1 及主生命周期。见 [流水线总览](/pipeline/overview)。

## UPDATE 模式

更新运行 Phase U1 至 U3。跳过评估、发现、模板生成与完整部署。见 [更新模式](/pipeline/update-mode)。

## 中断恢复

首次部署中断时，Sealos Deploy 识别已完成的评估、官方模板选择、镜像构建或模板生成。

Agent 仅在产物仍与当前项目和当前选择匹配时可恢复。官方模板进入 Phase 5 前须再次对照 [labring-actions/templates `kb-0.9/template`](https://github.com/labring-actions/templates/tree/kb-0.9/template) 验证。Agent 不得仅凭本地记录和 YAML 信任。

否则从合适的较早阶段重新开始。

## GitHub URL 桥接状态

GitHub URL 部署使用临时 checkout。项目目录中的 `.sealos/state.json` 不能作为清理后下次运行的唯一依据。

对于 GitHub 来源，Sealos Deploy 在以下路径保存稳定的桥接副本：

```
~/.sealos/deployments/github.com/<owner>/<repo>/state.json
```

桥接目录仅包含已验证的 `state.json`。Agent 在新 checkout 上于部署模式识别前恢复它。仅在 [Phase 7](/pipeline/phases/phase-7-post-deploy) 成功且完整状态通过 schema 验证后更新。

构建结果、模板及其他运行本地产物不复制到桥接目录。
