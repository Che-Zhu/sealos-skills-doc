## 目的

Phase 2 同时确认两件事：项目发布或使用的镜像，以及最终部署须保留的服务与依赖。它不是找到第一个镜像就停止的搜索。

镜像证据与运行时拓扑分别收集。

## 输入

| 输入 | 来源 |
| --- | --- |
| `analysis.json` | Phase 1 |
| 项目源码与文档 | `WORK_DIR` |

## 输出

| 输出 | 路径 | 说明 |
| --- | --- | --- |
| 部署源记录 | `.sealos/analysis.json` → `deployment_source` | 类型、路径、`source_hash`、证据 |
| 镜像清单 | `.sealos/analysis.json` → `image_inventory` | 选择器解析为 `repository@sha256:digest` |
| 服务清单 | `.sealos/analysis.json` → `service_inventory` | 含数据库与 worker 的完整服务列表 |
| 渲染源 | `.sealos/deployment-source/rendered.yaml` | 仅 Helm/Kubernetes 路径 |

部署源类型见 [部署源](/pipeline/deployment-sources)。

## 镜像证据顺序

1. README 中的镜像用法
2. CI 发布或推送目标
3. Compose 各服务的 `image` 或 `build`
4. Helm values、渲染 chart、官方文档镜像引用
5. 原生 Kubernetes 清单镜像引用

Agent 不得从组织或仓库名猜测 Docker Hub 或 GHCR 镜像。不得将模糊搜索结果视为可部署。README 中仅用于本地 `docker build -t` 的标签不是已发布镜像。Dockerfile `FROM` 是构建基础，不是项目已发布应用镜像。

## 拓扑证据顺序

1. 根目录或项目指定的 Compose 文件
2. 含 `Chart.yaml` 与 templates 的 Helm chart
3. 声明的原生 Kubernetes YAML
4. 无显式拓扑时的隐式路径

`implicit-single-service` 是兼容性产物名称。表示未采用 Compose、Helm 或 Kubernetes 拓扑。不表示仓库根即应用，也不表示只能有一个服务。

## Digest 规则

`latest`、`stable`、版本标签、digest 与省略标签均为有效项目输入。Agent 保留项目选择器并解析为不可变 digest。Phase 2 不预筛第三方镜像 CPU 架构。兼容性在 Phase 6 和 6.5 判断。

检测器输出是证据，不是最终裁决。隐式路径上 Agent 须确认镜像归属、服务边界与构建上下文。

## 构建跳过规则

按服务：

- 已解析不可变 digest → 复用，该服务跳过 Phase 3 和 4
- 仅 `build`、无 digest、有可信源码 → Phase 3 和 4
- Phase 5 转为 KubeBlocks 的数据库可跳过容器构建

仅当每个最终容器工作负载都有可复用镜像时，流程直接跳到 Phase 5。

数据库与基础设施不因非主应用镜像而被移除。

## 停止条件

| 结果 | 条件 |
| --- | --- |
| **CONTINUE → Phase 5** | 所有容器工作负载有可复用 digest |
| **CONTINUE → Phase 3** | 一个或多个服务需要构建定义 |
| **STOP** | 必需拓扑证据无法解析 |

## 验收标准

- `deployment_source`、`image_inventory`、`service_inventory` 已更新于 `analysis.json`
- 无猜测镜像名
- 完整拓扑保留，含数据库、队列、缓存、worker
