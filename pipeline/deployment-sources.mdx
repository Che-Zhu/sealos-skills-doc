## 来源类型

| 来源 | 检测 | 所需工具 |
| --- | --- | --- |
| 官方模板 | Phase 1 与 [`kb-0.9/template`](https://github.com/labring-actions/templates/tree/kb-0.9/template) 精确匹配 | 无（快速路径） |
| Docker Compose | `.sealos/phase-2/docker-compose.yml`（Phase 2 canonical） | kompose |
| Helm | `Chart.yaml` 或 chart 目录 | Helm 3+ |
| Kubernetes | 单个原生 manifest 文件 | Python/PyYAML |

标准构建路径中，部署源由 Phase 2 写入 `deployment-plan.json` 的 `deployment_source` 字段。Phase 4 直接读取该指针，不再重新侦察。

## 来源选择优先级

Phase 2 在侦察后按以下优先级选定**唯一** `deployment_source`：

1. **Helm** — chart 根目录
2. **Kubernetes** — 单个 manifest 文件
3. **Compose** — 生成或归一化到 `.sealos/phase-2/docker-compose.yml`

Helm 与 Kubernetes 同时存在时，Helm 优先。多个同类来源冲突时，须从 README、CI、文档确定主拓扑，不得猜测。

一次 Sealos 部署须覆盖全部相关组件（数据库、队列、缓存、worker）。Phase 4 不得因非主应用组件而丢弃依赖。

## 条件性源码物化

Git LFS、子模块等机制仅在仓库声明时安装与获取。见 [Phase 0](/pipeline/phases/phase-0-preflight)。

## 拓扑保留

`deployment_source` 所指文件（或 chart 渲染结果）须包含完整运行时拓扑。仅构建的组件与最终运行时拓扑分开处理；Phase 3 的 digest 在 Phase 4 从 `analysis.json` → `build_result` 写回部署源对应的工作负载。
