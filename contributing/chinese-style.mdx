本文档定义本站**中文 SSOT** 的写作规则。规则源自 [ASD-STE100 简明技术英语](https://www.asd-ste100.org) 的 pragmatic 模式，并适配中文技术文档。

<Note>
首页、营销文案不适用本规范。本规范用于流水线契约、技能说明与 normative 规格页。
</Note>

## 两种文体

| | 程序性（操作说明） | 描述性（解释说明） |
| --- | --- | --- |
| 用途 | 告诉读者做什么 | 说明事物是什么、做什么 |
| 语气 | 祈使句：「安装插件。」 | 一般现在时 |
| 句长上限 | **40 字** | **50 字** |
| 单元规则 | 一句一条指令 | 一段一个主题，每段不超过 6 句 |

不要在同一段落混用两种文体。快速开始章节是程序性；架构说明是描述性。程序性段落中的 Note 按描述性规则写。

## 词汇纪律

**一个概念，一个词。** 全文统一术语，禁止同义轮换。

| 概念 | 统一用词 | 禁止轮换 |
| --- | --- | --- |
| 检查/验证/确认 | **核对** | 检查、验证、确认、确保 |
| 配置 | **配置** | 设置、选项、config |
| 删除 | **删除** | 移除、销毁（按语义区分后固定一种） |
| 错误 | **错误** | 问题、故障（操作失败用「失败」） |
| 运行 | **运行** | 执行、调用、启动 |

领域术语保留英文或项目固定写法：`Phase`、`digest`、`kubeconfig`、`GHCR`、`.sealos/`。

## 句式规则

1. **短句优先。** 一句只传达一个事实或一条指令。
2. **主动语态。** 「Agent 写入 `state.json`」，不写「`state.json` 被写入」。
3. **条件在前。** 「若构建失败，读取日志。」不写「构建失败时读取日志」放在句尾含糊指代。
4. **要求用「必须」「不得」。** 禁止用「应该」「可以」表达硬性要求。建议性内容写成事实，或删除。
5. **禁止填充词。** 删除「值得注意的是」「简单来说」「无缝」「强大」等无信息词。
6. **禁止分号。** 拆成两句。

## 程序性写作

- 一句一条指令。
- 使用祈使句：「选择工作空间。」
- 警告与注意放在指令之前：「警告：不得对生产环境使用 `--force`。」

## 描述性写作（规范页）

- 规范要求写「必须」「不得」，不用「应该」。
- 每个 Phase 页使用固定结构：目的、输入、输出、前置条件、流程、停止条件、验收标准。
- 技术标识符（路径、命令、字段名）保持原样，不翻译。

## 自检清单

发布前必须完成：

1. 找出最长的 3 句话。程序性超过 40 字、描述性超过 50 字则拆分。
2. 全文搜索「应该」「可以」（表要求时）、「等等」「即」作缩写用法。
3. 核对术语表：同一概念是否只有一个词。
4. 规范页每条「必须/不得」能否对应实现或 eval 验收。

## 与实现对照

撰写或修订中文规范时，对照 [`sealos-skills` 的 `codex/review-sealos-deploy` 分支](https://github.com/labring/sealos-skills/tree/codex/review-sealos-deploy) 中的实现与 schema。发现差异时，以根路径中文 SSOT 为准修正实现，或在 PR 中明确记录有意偏离。

## 英文翻译

`en/` 目录为译文。翻译时遵循同一 STE 原则（英文句长：程序性 20 词、描述性 25 词）。先定中文，再译英文。
